1. Document Purpose and Scope
This document is the detailed data-design follow-on to the approved MVP Technical Solution Architecture. It translates the logical domains into proposed PostgreSQL tables, 
relationships, keys, column types, row-level-security ownership, effective-date controls, indexes, classifications and retention expectations. It covers the Phase-One MVP and 
intentionally excludes full TaskOps, advanced assets, benefits administration and predictive AI models.
The architecture baseline is source-derived. Specific table names, columns, types and indexes are proposed implementation detail and must be reviewed by domain owners, 
payroll specialists, security, privacy, QA and implementation teams before production migration scripts are approved.

4. Architecture Data Baseline
Decision area Approved baseline
Authoritative store PostgreSQL is the transactional system of record. Redis, reports, exports and caches are derived.
Tenancy Shared PostgreSQL database and shared schema. Every tenant-owned row includes non-null tenant_id.
Isolation JWT membership, application authorisation, transaction-local tenant context and PostgreSQL RLS.
Architecture Modular monolith; each domain owns its tables and writes through domain application services.
Time Timestamps stored in UTC; business dates and source time zones retained separately.
Money Fixed-precision decimal with explicit ISO currency. Floating point is prohibited.
History Organisation, employment, shifts, policies and salary use effective dates; high-impact records use 
versions.
Evidence Raw attendance, leave ledger, workflow actions, audit and outbox events are append-oriented.
Payroll Each payroll version snapshots source inputs, formula versions, employee results and component 
lines.
Documents Binary objects live in encrypted object storage; PostgreSQL stores metadata and access controls.
5. PostgreSQL Naming and Type Standards
Area Standard Rationale
Names snake_case; singular table names; descriptive foreign-key columns Consistent SQL, migration and repository naming.
Primary key uuid using gen_random_uuid() Globally unique, non-sequential external references.
Tenant ownership tenant_id uuid NOT NULL Mandatory RLS partitioning key.
Timestamp timestamptz stored in UTC Unambiguous cross-region event time.
Business date date Payroll/leave/roster date independent of instant.
Local time time plus IANA timezone reference Shift definitions and source evidence.
Money numeric(19,4) plus char(3) currency_code Deterministic payroll arithmetic.
Percent/rate numeric(19,6) or numeric(9,6) Avoid floating-point drift.
Durations integer minutes Simple attendance and payroll integration.
Quantity numeric(10,4) Supports leave days/hours and fractional units.
State varchar with CHECK or PostgreSQL enum only after governance review Explicit lifecycle values without uncontrolled text.
Configuration jsonb with schema validation Flexible rules; never arbitrary SQL or unvalidated shape.

6. Tenant Isolation and Row-Level Security
Tenant isolation is mandatory across API requests, application services, jobs, exports, connectors and support tooling. RLS is defence in depth, not a replacement for application 
authorisation. Global tables such as plan, entitlement, permission and deployment_region do not carry tenant_id; every customer-owned table does.
Control Database requirement
Transaction context Application starts a transaction and sets app.tenant_id using SET LOCAL or set_config(..., true).
RLS policy USING and WITH CHECK compare tenant_id with current_setting(app.tenant_id).
Connection pool Tenant setting is transaction-local and cannot leak across pooled connections.
Foreign keys Application and composite constraints prevent cross-tenant references.
Unique constraints Tenant-scoped uniqueness begins with tenant_id.
Jobs/events Worker re-establishes tenant context from trusted job/event metadata before database access.
Support Support grant establishes explicit, time-limited tenant access; no silent impersonation.
Testing Negative tests attempt cross-tenant reads/writes through repositories, APIs, jobs and exports.
-- Transaction-local tenant context
BEGIN;
SELECT set_config('app.tenant_id', :tenant_uuid, true);
ALTER TABLE employee ENABLE ROW LEVEL SECURITY;
ALTER TABLE employee FORCE ROW LEVEL SECURITY;
CREATE POLICY employee_tenant_rls ON employee
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
COMMIT;
Critical control
Database owners used by the application must not bypass RLS. Migration and break-glass roles are separate, restricted, monitored and never used for ordinary application 
traffic.

8.1 Relationship and Integrity Principles
Principle Implementation requirement
Domain ownership Only the owning domain repository/application service writes its tables. Cross-domain updates use explicit 
service calls and outbox events.
Tenant consistency All referenced tenant-owned records must belong to the same tenant. Composite foreign keys or triggers are 
used where normal FK structure cannot prove it.
Effective dates No overlapping current employment, organisation, shift, salary or policy assignment ranges unless the 
business explicitly permits multiple relationship types.
Append-only evidence Raw events, leave ledger, workflow actions, audit and approved payroll evidence are not updated to erase 
history.
Convenience pointers Fields such as current_employment_id or current_version_id are cache-like pointers and must be reconciled 
with authoritative history.
Deletion Approved payroll, attendance corrections, acknowledgements and audit evidence are reversed/superseded, 
not deleted.
Source snapshots Payroll and submitted workflows preserve the inputs/configuration version selected at the time.
Referential lifecycle Parent records with history are deactivated or ended; cascading hard deletes are avoided for business 
evidence.

11. Indexing, Partitioning and Query Strategy
Area Proposed strategy
Tenant-leading indexes Interactive tenant queries begin with tenant_id, followed by status/date/foreign key according to 
measured filters.
Unique keys Tenant-specific unique constraints include tenant_id. Global catalogue codes are globally unique.
Effective history Index (tenant_id, entity_id, effective_from DESC); exclusion constraints prevent invalid overlapping 
periods.
Attendance Index employee/time and processing status. Consider time partitioning only after measured volume 
and operational review.
Payroll Batch-fetch source inputs; avoid N+1 employee queries; index version/result and exception status.
Workflow Index assigned_user_id, status and due_at for approval inbox and escalation jobs.
Audit/outbox BRIN or time partitions at scale; pending outbox index is partial on status=PENDING.
Reporting Use tenant-safe views/materialised views; asynchronous exports for large results; replicas only after 
measured need.
Search Use tsvector/GIN for employee directory. Do not use wildcard scans over encrypted sensitive fields.
JSONB GIN only for stable validated query patterns; do not use JSONB as a substitute for core relational 
columns.
Performance rule
Indexes are hypotheses until validated with representative tenants, attendance bursts, payroll batches and report workloads. Every added index has write/storage cost and an 
accountable query pattern.

Pattern Applies to Rule
Effective range Employment, org assignment, manager, shift, policy, salary effective_from is inclusive; effective_to is exclusive; overlapping active 
ranges are prohibited where only one record may apply.
Definition version Workflow, leave policy, attendance policy, shift, salary 
component/structure
Published version is immutable. New business rule creates a later 
version.
Calculation version Attendance day and payroll version Recalculation creates a new version linked to superseded evidence.
Ledger Leave balance Balance is sum of append-only entries; snapshot is derived only.
Raw event Attendance/integration Original received evidence is immutable; corrections create new 
records.
Action history Workflow/audit/access Actions are append-only with actor, time and correlation.
Approved payroll Payroll version, lines, payslips, exports Approved version is locked. Reopening creates a new controlled 
version; generated outputs reference approved version only.

14. Migration, Deployment and Backfill Rules
 Use expand-contract migrations: add structures, deploy compatible code, backfill safely, then remove obsolete structures in a later release.
 Every tenant-owned table migration verifies tenant_id NOT NULL, RLS enabled/forced, policies present and application role cannot bypass RLS.
 Backfills run in bounded tenant-aware batches with checkpoint, retry, progress, dead-letter handling and reconciliation totals.
 Do not perform long data rewrites in application startup. Use a controlled migration or background job with advisory lock.
 Migrations are tested from an empty database and from the previous supported production schema using representative data volume.

19. Database Acceptance Criteria
1. Every tenant-owned table contains non-null tenant_id, RLS is enabled and forced, and the application role cannot bypass it.
2. Automated tests prove no cross-tenant read, write, job, report, export or document metadata access.
3. Global and tenant-scoped unique constraints follow the approved ownership model.
4. Effective-dated employment, organisation, reporting, shift, policy and salary records reject invalid overlap.
5. Raw attendance, leave ledger, workflow actions, audit, outbox and approved payroll evidence are append-oriented.
6. Payroll source inputs, formula versions, results and component lines can reproduce every approved payslip.
7. Sensitive identifiers and bank data use encryption/hash patterns and are masked in ordinary reads and exports.
8. Documents reference scanned encrypted objects and legal hold/retention prevents unauthorised deletion.
9. Indexes support representative employee, approval, attendance, payroll and report workloads without unacceptable write overhead.
10. Migrations pass empty-database, previous-version, backfill-restart and production-scale rehearsal tests.
11. Backup and restore reproduce schema, data, RLS, extensions, constraints and critical object references.
12. Product, architecture, backend/data, security/privacy, payroll, QA and DevOps approve the production schema baseline.
