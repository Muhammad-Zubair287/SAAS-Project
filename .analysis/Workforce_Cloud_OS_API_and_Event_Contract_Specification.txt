1. Document Purpose and Scope
Build-ready external and internal contract rules for the approved MVP.
This document defines the public REST API, reusable schemas, endpoint-level security, error model, 
idempotency, concurrency, asynchronous operation model, domain-event envelope, event catalogue, outbound 
webhook delivery and contract-governance practices for Workforce Cloud OS. It covers tenant administration, 
identity, organisation, Core HR, onboarding, documents, attendance, shifts, leave, workflow, payroll, 
notifications, reporting, integrations, subscription controls, audit and platform operations.
Source-derived baseline
The approved architecture requires REST-first versioned APIs, stable validation and error contracts, idempotency 
for external writes, signed webhooks, generated OpenAPI documentation, transaction-scoped tenant context, 
PostgreSQL RLS and a transactional outbox. Exact route names, DTO field sets, error codes, rate-limit classes and 
event payload details in this document are proposed implementation contracts derived from that baseline.

2. Contract Principles and Non-Negotiable Rules
 Tenant context comes from trusted authentication and routing context; normal tenant endpoints never 
accept an arbitrary tenant_id parameter.
 APIs represent business resources and commands, not generic CRUD access to database tables.
 The API is the authoritative permission boundary even when the user interface hides an action.
 High-impact writes use optimistic concurrency, explicit confirmation, audit evidence and MFA where 
configured.
 External and retryable writes are idempotent. At-least-once event consumers are also idempotent.
 Money is a fixed-precision decimal string plus currency. Floating-point values are prohibited.
 Business dates and UTC timestamps are distinct. Date/time values use ISO 8601 and explicit offsets when 
provided by a source.
 Sensitive salary, bank, identification, medical, location and document data is minimised, masked and 
excluded from logs and notification bodies.
 Breaking contract changes require a new major API or event version; additive changes follow documented 
compatibility rules.

4. Protocol, Base URL and Representation
Concern Contract
Transport HTTPS only. TLS policy is controlled by the platform edge.
Base path /api/v1 for the first stable API generation.
Media type application/json; charset=utf-8. File bytes use signed object-
storage URLs.
Dates Business dates: YYYY-MM-DD. Date/time: RFC 3339 / ISO 8601 
with timezone offset when source-local.
Identifiers Opaque UUID or time-sortable IDs. Clients must not infer type, 
chronology or permission from an ID.
Naming camelCase JSON properties; plural resource collections; 
command sub-resources for high-impact transitions.
Nullability Omitted means not provided; null is accepted only where the 
schema explicitly allows clearing.
Unknown fields Rejected on strict command DTOs; may be ignored in 
event/webhook consumers according to compatibility policy.
Compression gzip/br supported at edge for suitable payloads.
Caching Private authorised reads may use ETag. Sensitive responses use 
Cache-Control: no-store.

9. Query, Filtering, Pagination and Concurrency
Concern Contract
Collection pagination Keyset/cursor pagination for employees, attendance, approvals, 
audit, payroll results and other large collections.
Cursor opacity Cursor is signed/opaque. Clients cannot construct or modify it.
Stable order Every paginated query has a deterministic tie-breaker, 
normally createdAt/id or business date/id.
Filtering Each endpoint allow-lists filter names, operators, ranges and 
maximum cardinality.
Search Normalised limited search fields only; no raw SQL-like query 
language.
Field selection Only documented sparse-field or column selection; permission 
applied per field.
Sorting Allow-listed fields and directions; sensitive computed fields 
may be unavailable.
Optimistic concurrency PATCH and high-risk transitions require If-Match or 
expectedVersion where concurrent edits matter.
Conflict response 412 VERSION_CONFLICT includes current version and safe 
reload link, not the complete sensitive record.
Bulk operations Bounded item count, per-item result, atomicity explicitly 
documented; heavy bulk operations are asynchronous.

10. Idempotency and Duplicate Protection
Figure 3 - Persistent idempotency behaviour for retry-safe writes.
Rule Definition
Key scope tenant + authenticated client/user + HTTP method + canonical 
route + Idempotency-Key.
Fingerprint Canonical request body hash and selected headers.
First request Create processing record before or within the business 
transaction as defined by endpoint.
Replay Same key and fingerprint returns the stored safe response and 
Replayed: true metadata where useful.
Conflict Same key with different fingerprint returns 409 
IDEMPOTENCY_KEY_REUSED.
In progress Return existing operation/status link. Do not start a parallel 
business operation.
Retention Endpoint-specific, long enough for realistic connector/client 
retry windows; high-risk payroll commands retained with 
audit evidence.
Client guidance Use one key per business intention, not one key per network 
attempt.

15. Event Architecture and Delivery Semantics
Figure 5 - Reliable event publication and idempotent consumption.
Concern Contract
Publication Business state and outbox row commit in one PostgreSQL 
transaction.
Delivery At least once. Exactly-once delivery is not claimed.
Consumer deduplication Consumer inbox keyed by eventId and consumer name; side 
effect and processed marker commit together.
Event identity Globally unique eventId. A retry reuses the same eventId.
Correlation correlationId follows the user/business flow. causationId 
identifies the command or event that directly caused this event.
Partitioning partitionKey preserves relevant aggregate ordering where the 
transport supports it.
Ordering Only guaranteed within the documented aggregate/partition 
and transport limits; consumers must not assume global 
ordering.
Immutability Published event payload is immutable. Corrections publish a 
later event.
Retention Internal event/outbox retention and public webhook retention 
are configured separately.
Privacy Events contain minimum identifiers and business values 
required by consumers. Documents, tokens, bank details and 
unnecessary private reasons are prohibited.

7 QA and performance test plan Contract, tenant isolation, payroll 
regression, load and resilience.
8 Engineering backlog and estimation Epics, stories, dependencies, owners, 
releases and resource plan.
33. Final Contract Recommendation
Workforce Cloud OS should publish one consistent contract platform rather than allowing each module to 
invent transport, errors, tenant context, idempotency or event envelopes. REST commands should remain close 
to business intentions, heavy work should use durable asynchronous operations, and all cross-module reactions 
should be driven by committed, versioned events. Payroll and attendance contracts must prioritise traceability 
and replay safety over superficial CRUD simplicity.
Contract statement
Stable REST resources and commands, explicit tenant-scoped authorisation, persistent idempotency, deterministic 
high-impact workflows, transactional events and signed external delivery.
