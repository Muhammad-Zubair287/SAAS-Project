1. Document Purpose and Architecture Scope
A build-ready technical blueprint for the approved MVP.
This document defines how Workforce Cloud OS should be implemented as a secure, scalable, multi-tenant 
workforce SaaS platform. It follows the approved BRD, module-by-module PRD, screen-level UX specification and 
enterprise design system. The architecture supports the Phase-One product scope: tenant administration, 
identity, organisation, Core HR, onboarding, attendance, shifts, leave, approvals, payroll, employee and manager 
self-service, notifications, reporting, imports, integrations, subscriptions and audit controls.
The document explains technology responsibilities, data ownership, security boundaries, integration patterns, 
deployment topology, delivery controls and operational requirements. It deliberately separates the MVP 
architecture from later product capabilities such as TaskOps, advanced assets, benefits, predictive AI and full 
global payroll.

3. Executive Architecture Summary
Workforce Cloud OS should launch as a modular monolith deployed on Kubernetes. The application is separated 
into domain modules that own their business rules and data. Modules communicate through explicit 
application-service interfaces and domain events. This approach avoids premature distributed-system 
complexity while preserving a clear path to extract independently scaling services later.
 Next.js provides the server-rendered and client-interactive web experience for platform, tenant, HR, payroll, 
manager and employee users.
 NestJS provides REST APIs, application services, background jobs and integration endpoints.
 PostgreSQL is the authoritative transactional database. Every tenant-owned row includes tenant_id and is 
protected by PostgreSQL row-level security.
 Redis supports caching, distributed locks, rate-limiting counters and background job queues. Redis is not the 
system of record.
 Object storage holds employee documents, exports and generated payslips through secure, time-limited 
access links.
 A transactional outbox publishes reliable domain events after database commits, allowing modules and 
integrations to react without unsafe dual writes.
 OpenTelemetry provides consistent logs, metrics and traces across web, API, workers and connectors.
 The reference cloud implementation uses AWS services, with a mapping to equivalent Azure and GCP 
services.
Primary architecture decision
Build one deployable application with independently testable domain modules. Extract services only when a domain 
needs independent scaling, release cadence, data isolation or operational ownership.

13. Multi-Tenant Architecture
Figure 4 - Tenant-isolated request flow and defence in depth.
The MVP uses a shared PostgreSQL database and shared schema. Every tenant-owned table contains a non-null 
tenant_id. Tenant isolation is enforced at multiple layers so that a defect in one control does not automatically 
create cross-tenant exposure.
Control layer Requirement
Request entry Tenant is resolved from the authenticated host, organisation 
selection or signed token claim.
JWT claims Token contains user identity, tenant membership, session and 
role references. Claims are verified, not trusted blindly.
Application authorisation Every use case checks permission and business scope such as 
legal entity, department or manager hierarchy.
Database transaction Application opens a transaction and sets the current tenant 
using a transaction-local database setting.
PostgreSQL RLS Policies compare row tenant_id with the database tenant 
context. Queries without valid context return no tenant data.
Jobs and events Queue messages contain tenant_id and correlation_id; workers 
re-establish tenant context before data access.

18. Data Integrity and Versioning Rules
 Use UUID or time-sortable unique identifiers for externally referenced records; never expose sequential 
database IDs as security controls.
 All tenant-owned primary and unique indexes include tenant_id where uniqueness is tenant scoped.
 Use optimistic concurrency or version columns for high-conflict administrative records.
 Do not delete approved payroll, attendance corrections, policy acknowledgements or audit evidence. Create 
reversals, adjustments or later versions.
 Payroll calculation stores the formula version and snapshots the source values used for the run.
 Policy changes create new versions and effective dates; in-flight requests keep the workflow and policy 
version selected at submission.
 Timestamps are stored in UTC. Business dates and time zones are retained separately for attendance and 
payroll interpretation.
 Money uses fixed-precision decimal types and an explicit currency code; floating-point types are prohibited 
for payroll amounts.
 Document objects use checksums and versioning to detect replacement or corruption.
 Schema constraints enforce required ownership and state transitions where practical, not only application 
validation.

19. Database Performance Strategy
Area Strategy
Indexes Composite indexes begin with tenant_id for tenant-scoped 
queries. Add date and status columns based on measured access

Attendance volume Partition raw attendance events by time only when volume 
justifies it; retain tenant_id indexes and idempotency key.

20. API Architecture
The product should expose versioned REST APIs for web and external integrations. APIs represent business 
actions, not generic table access. The same application services are used by UI controllers, connectors and 
background jobs.
API concern Requirement
Versioning Use a stable /api/v1 prefix and explicit deprecation policy. Avoid 
breaking field semantics.
Resource naming Use tenant-neutral routes because tenant comes from trusted 
context; do not allow callers to select arbitrary tenant_id.
Validation Validate syntax, business preconditions and authorisation. 
Return field-level errors suitable for the UX.
Idempotency Require idempotency keys for attendance ingestion, 
payment/export triggers and external write operations.
Pagination Cursor or stable keyset pagination for large lists; offset 
pagination only for bounded administrative data.
Filtering Allow approved filter fields; reject unbounded arbitrary query 
construction.
Errors Structured error code, user-safe message, correlation ID and 
field details. Never expose stack traces.
Rate limiting Apply by tenant, user, client and endpoint risk. Attendance 
ingestion receives separate limits.
Webhooks Signed payloads, event IDs, retry with backoff, delivery history 
and endpoint disablement after repeated failure.
Documentation Generate OpenAPI; publish partner-specific scopes and

23. Leave and Policy Architecture
 Leave balances are represented as a ledger of grants, accruals, reservations, approvals, cancellations, 
adjustments and expiries.
 A leave request reserves entitlement during approval where tenant policy requires it; final approval posts 
the consumption entry.
 Policy resolution uses employee, legal entity, employment type, grade, service date and effective date.
 The request stores the selected policy version and calculated day breakdown so later policy changes do not 
rewrite history.
 Approved unpaid leave emits a payroll-impact event with effective dates and quantity.
 Private attachments and medical details use document classifications and need-to-know permissions.
 Calendar views use read models and never expose private reasons to managers without permission.

26. Payroll Calculation Controls
 Use a formula registry with unique version, effective dates, component order and test fixtures.
 Use decimal arithmetic with defined rounding at component and net-pay levels.
 Persist the raw source inputs and calculated outputs for every employee in the payroll version.
 Prevent approval while blocking errors exist. Overrides require permission, reason and audit.
 Run payroll calculation as bounded background jobs with per-tenant concurrency controls.
 Calculate chunk results independently but finalise aggregate totals only after all chunks succeed.
 Use database advisory or distributed locks so the same payroll period is not calculated or approved 
concurrently.
 Generate payslips and exports only from the approved locked version.
 Parallel-payroll comparison is a release gate for new customers and rule-pack changes.
 Maintain a payroll regression suite covering full month, joiner, exit, unpaid leave, overtime, adjustment and 
reopening scenarios.

31. Connector Runtime
 Connectors run in isolated worker deployments with separate network policies and credentials.
 Connector configuration references secrets; credentials are never returned to the browser after saving.
 Each sync run records source window, item counts, errors, retries and last successful checkpoint.
 External identifiers are mapped through explicit mapping tables and cannot silently create employees.
 Incoming records are validated and normalised before domain commands are accepted.
 Reconciliation queues surface unmapped, duplicate or conflicting records to administrators.
 Connector software versions and configuration changes are audit logged.
 On-prem connectors initiate outbound mutually authenticated TLS connections or polling to avoid customer 
firewall exposure.

47. Data Migration Architecture
Customer migration is a controlled import pipeline, not direct database loading. Every migration run is tenant 
scoped, validated, previewed and reconciled.
1. Create approved template and field mapping for organisation, employees, salary structures, leave balances 
and attendance history.
2. Upload file to quarantine storage and validate file type, size and malware state.
3. Parse into a staging area associated with tenant and import job.
4. Validate required fields, duplicates, references, dates, currencies and policy assignments.
5. Present error and warning counts; allow downloadable error file and corrected re-upload.
6. Preview the records and expected creates or updates before commitment.
7. Commit valid records through domain application services in controlled batches.
8. Generate import summary, unresolved issues and reconciliation report.
9. Retain import source checksum, actor, mappings and audit record.
10. For payroll customers, complete parallel payroll before production activation.
