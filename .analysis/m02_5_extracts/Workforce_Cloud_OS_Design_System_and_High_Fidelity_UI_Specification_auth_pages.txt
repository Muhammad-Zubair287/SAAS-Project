1. Document Purpose and Handoff Scope
A build-ready visual specification for Figma, design review and frontend implementation.
This document defines the complete visual language and high-fidelity web experience for the Workforce Cloud OS 
MVP. It translates the approved BRD, PRD, user-flow specification and low-fidelity wireframe pack into an 
enterprise UI system that can be recreated directly in Figma.
Figma handoff outcome
The design team should be able to create variables, components, high-fidelity frames and clickable prototype 
journeys without making new product decisions. Any decision not explicitly covered must be raised as a product 
question rather than silently invented.
Included deliverables
 Brand and product visual direction for enterprise workforce software.
 Figma-ready colour, typography, spacing, grid, radius, border, shadow and motion tokens.
 Reusable component specifications for administrative, manager and employee experiences.
 High-fidelity reference designs for thirteen critical MVP screens.
 Complete module-by-module screen inventory using the approved screen IDs.
 Responsive, accessibility, privacy, localisation and right-to-left requirements.
 Figma file architecture, naming conventions, prototype journeys and handoff checklist.
Design boundaries
 The document defines UI and interaction design; it does not replace the business rules in the BRD or functional 
behaviour in the PRD.
 Sample employee, payroll and attendance data is illustrative and must not be treated as production data.
 The initial product uses a responsive web application. Native mobile design can reuse employee self-service 
patterns in a later phase.
 TaskOps, advanced assets, benefits, gamification and predictive AI remain later-phase modules, but token and 
component choices must not block them.
2. Experience Strategy
The product should feel like an enterprise operating system, not a collection of disconnected HR 
tools.
Experience promise
Every workforce event should be understandable, traceable and connected to the next business action. The 
interface must answer: What is happening? What action is required? Who is responsible? What is the current 
status? What happens next?
Design principles
Principle Design implication
Connected by default Employee, attendance, leave, payroll and approval information should share context and 
avoid duplicate user entry.
Confidence before speed Payroll, access and employment-status decisions require impact summaries, validation and 
explicit confirmation.

Motion
 Fast feedback: 120-160 ms for hover, focus and selection.
 Standard transition: 200-240 ms for drawers, tabs and expanding details.
 Complex process: use progress indication rather than decorative animation.
 Respect reduced-motion preferences. Do not animate payroll amounts or employee status in a distracting way.
 Success animation may be used briefly for employee check-in, request submission and onboarding completion.
8. Iconography, Illustration and Data Visualisation
Icon system
 Use one consistent outline icon family such as Lucide with 1.75-2 px stroke.
 Standard sizes: 16 px compact, 20 px default, 24 px navigation and 32 px empty-state illustration.
 Pair unfamiliar icons with text labels. Icon-only actions require accessible names and tooltips.
 Directional icons must mirror in right-to-left layouts. Universal symbols such as check, warning and search do 
not mirror.
Illustration direction
 Use minimal geometric cloud, people and workflow illustrations only in empty, onboarding and marketing 
states.
 Do not use cartoon people in payroll, audit, security or compliance screens.

9. Accessibility, Localisation and Privacy
Accessibility requirements
 Target WCAG AA for colour contrast, keyboard navigation, focus visibility, labels and error association.
 Touch targets should be at least 44 x 44 px for mobile high-frequency actions.
 All status badges include readable text and do not depend on colour alone.
 Tables include programmatic headers; charts include text summaries or data-table alternatives.
 Modals trap focus, drawers restore focus, and dynamic success or error messages are announced.
 Every critical workflow must be operable without a mouse.
Urdu and right-to-left readiness
 Create Figma variables for direction-aware spacing and start/end alignment.
 Mirror sidebars, breadcrumbs, chevrons, timelines and directional icons in RTL mode.
 Keep payroll numbers, dates, employee IDs and currency values readable in mixed-direction content.
 Allow longer Urdu labels and place form labels above controls on smaller screens.
 Maintain an approved product terminology glossary for HR, payroll, attendance and policy terms.

Navigation behaviour
 Permissions remove unavailable destinations rather than showing disabled navigation.
 Module entitlements and role permissions are both required before a screen is visible.
 Users with multiple roles receive one combined navigation structure without duplicate items.
 Deep links display a safe access-denied state if the user no longer has permission.
 The employee mobile shell uses a maximum of five bottom navigation items; secondary destinations move to 
More.

22. Appendix A - Standard Status Vocabulary
Semantic group Approved labels
Neutral Draft, not started, inactive, archived

Positive Active, approved, complete, ready, healthy
Warning Due soon, late, incomplete, needs review, expiring
Critical Rejected, failed, blocked, overdue, suspended
Locked Closed, locked, published, finalised

===== PAGE 41 =====
Status writing rules
 Use one label for one system state. Do not alternate between Pending, Waiting and In progress without product 
meaning.
 Status labels should describe the record, not instruct the user. Use a separate action label for what to do next.
 Past-tense labels indicate a completed action; active labels indicate current process state.
 Locked and published are not interchangeable: locked prevents change, published exposes approved output to 
employees.
23. Appendix B - Standard Empty, Error and Loading 
States
State Design requirement
First-use empty Explain the capability and provide the first permitted action.
Filtered empty State that no records match and provide Reset filters.
Permission empty Explain that access is restricted without revealing protected data.
Integration empty Identify the missing connection and link to configuration.
Inline validation Place below the field; explain exactly how to correct it.
Page error State what failed, whether changes were saved, retry action and support reference.
Partial failure Keep available data visible and mark stale or unavailable sections.
Loading skeleton Match the expected layout and avoid large shifts.
Long process Show progress, stage, elapsed context, safe navigation and completion notification.
Offline attendance Preserve clear retry behaviour and prevent duplicate event creation.
