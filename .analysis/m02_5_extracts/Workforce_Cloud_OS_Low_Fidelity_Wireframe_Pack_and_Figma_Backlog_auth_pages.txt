1. Design Strategy and Low-Fidelity Conventions
1.1 Design Outcomes
Outcome Low-Fidelity Requirement
Clarity Every screen must make the current status, next action 
and responsible role visible.
Connected workflows Source records, approval actions and downstream 
impacts must be linked rather than represented as 
isolated screens.
Error prevention Validation, readiness checks and impact summaries 
appear before high-impact submission or approval.
Mobile employee experience Attendance, leave, requests, notifications and payslips are 
designed mobile first.
Secure administration Sensitive payroll, bank, identity, audit and support-access 
screens use explicit permissions and confirmation states.
Scalable configuration Tenant policy differences are represented through 
settings, rules and workflows rather than customer-
specific layouts.
1.2 Fidelity Rules
 Use greyscale only. Colour is reserved for later semantic and brand design decisions.
 Use realistic field labels and data categories, but use synthetic names and values.
 Represent charts as simple bars, lines or labelled placeholders; the goal is hierarchy, not final data 
visualisation.
 Show one primary action per screen. Secondary actions belong in contextual menus or outlined buttons.
 Annotate permission differences, system-generated values, background processing and integration 
dependencies.
 Create empty, loading, error, warning, success, disabled and read-only states for reusable components before 
duplicating screens.

2.3 Shell Rules
 Desktop uses a persistent left navigation and top utility bar. The current tenant and current module must 
always remain visible.
 Employee mobile uses a five-item bottom navigation: Home, Attendance, Requests, Payslips and More.
 Manager mobile uses Home, Team, Approvals, Notifications and More.
 Screens available through multiple roles use one shared frame with permission annotations, not separate 
duplicated designs.
 High-impact actions such as payroll approval, tenant suspension, payroll reopening and role changes require 
a review or confirmation state.

5. State and Responsive Matrix
5.1 Required Reusable States
State When Required Design Expectation
Empty No records, no configuration or no search 
results.
Explain why the page is empty and 
provide the next permitted action.
Loading Initial page load, background job, payroll 
calculation, import or export.
Use skeletons for pages and explicit 
progress for jobs.
Validation error User input violates data or business rules. Show field-level message and preserve 
valid inputs.
Business warning Action is allowed but has operational 
impact.
Explain consequence and require 
acknowledgement where appropriate.
System failure API, integration or infrastructure action 
fails.
State whether data was saved and provide 
retry or support reference.
Success Create, submit, approve, publish or export 
completes.
Confirm the exact result and update source 
status immediately.
Read-only Locked payroll, auditor view, historical 
policy or inactive record.
Remove edit controls and explain why the 
record is locked.
No permission User opens an inaccessible deep link. Use a controlled access message without 
exposing record details.
Offline/network interruption Mobile attendance or employee action 
cannot reach the service.
Avoid duplicate submission; provide safe 
retry and current local status.

7.1 Prototype Interaction Rules
 Use overlays for confirmations, rejection comments and compact review actions; use full frames for long 
forms and record details.
 Prototype at least one validation failure and one system/integration failure inside each critical journey.
 Use variables or clearly labelled duplicated frames for role and status differences; do not make invisible 
prototype logic difficult to maintain.
 Every prototype end state should show the updated source record, not only a temporary success toast.
 For payroll, use realistic but synthetic employee counts and PKR values. Never use customer or employee 
production data.
